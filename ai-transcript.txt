  Requirements (final draft)

  Functional
  1. Upload documents at runtime: PDF, TXT and MD files, several at a time,
     through the web UI or the REST API.
  2. Build the index automatically: each upload is parsed, split into chunks,
     embedded and added to the active corpus. No restart or code change is
     needed.
  3. Ask questions and get grounded answers:
     - Claude answers only from the retrieved passages.
     - It cites its sources inline, as [1], [2] with the file name and page
       number.
     - If the documents don't contain the answer, it says so instead of
       guessing.
  4. Use one corpus per session: there's a single active document set (assumed
     to be one per server instance, not one per browser). You can list the files
     in it, add more, or reset it to start over with a different set.
  5. Stream answers into the UI as they're generated.

  Non-functional
  - The API key and settings live in .env: model, chunk size, top-k.
  - Embeddings run locally, so the only external dependency is the Anthropic
    API.
  - The corpus is saved to disk, so it survives a server restart.
  - There are clear errors for unsupported files, empty or scanned PDFs with no
    text, and a missing API key.

  Out of scope: OCR for scanned PDFs, user accounts and login, multiple named
  knowledge bases, URL ingestion, DOCX.

  Architecture

  Browser (static HTML/JS)
     │  upload / ask / reset
  FastAPI ──► Ingestion: parse (pypdf / text) → chunk (~800 chars, 150 overlap,
  keeps page no.)

  ChromaDB (local, persistent)
     └────► Query: embed question → top-k=5 retrieval → prompt with numbered
  context

⏺ Milestone 3 is finished and committed (0276fa8). All 53 tests pass.

  What was added, in app/ingestion/:
  - Upload checks in validation.py (app/ingestion/validation.py), which run
    before any file is parsed:
    - Limits: the number of files per upload and the number of documents per
      session.
    - File checks: file size, and the extension (.pdf or .txt, case doesn't
      matter).
    - Content matches the extension: a .pdf must actually start like a PDF, and
      a .txt must not be binary.
    - Filenames: folder paths are stripped from uploaded names, so a name like
      ../../x.pdf becomes x.pdf.
  - Reading files in loaders.py (app/ingestion/loaders.py):
    - PDFs are read page by page so page numbers are kept. Uploads over the page
      limit, password-protected files, corrupt files and PDFs with no text
      (such as scanned ones) are rejected with a clear message.
    - Text files are read as UTF-8, falling back to Latin-1 for older encodings.
  - Chunking in chunker.py (app/ingestion/chunker.py) splits text at paragraph
    breaks where it can, then at lines, sentences and words. Chunks are about
    800 characters, and the end of each chunk is repeated at the start of the
    next one. A chunk never crosses a page boundary, so every citation points to
    exactly one page.
  - Error codes: each kind of rejection maps to its own HTTP status, so
    milestone 4's upload endpoint can return errors directly. Unsupported type
    is 415, too large or too many pages is 413, unreadable is 422, and session
    document limit reached is 409.
  - Tests: tests/pdf_utils.py builds real PDFs by hand, so the tests read actual
    PDFs without any mocking. There are 36 new tests, covering every limit,
    both file formats, the error cases and how chunks are sized and overlap.

⏺ Milestone 4 is finished and committed (d8490dd). 78 fast tests pass, plus 1
  slow test that uses the real embedding model.

  What was added:
  - Vector store in app/store.py:
    - Separation: each session gets its own ChromaDB collection, so a search in
      one session can't reach another session's documents.
    - Citations: each chunk is stored with its file name and page number.
    - Embeddings: the BGE model loads in the background when the server starts,
      so the first upload isn't slow. BGE is also given the phrasing it expects
      for search queries.
  - Upload handling in app/documents.py:
    - All or nothing: every file in an upload is checked and parsed before
      anything is indexed. If one file is rejected, or indexing fails partway,
      nothing from that upload is kept.
    - Duplicates: the same file content can't be added to a session twice, even
      under a different name.
    - Concurrent uploads: simultaneous uploads to the same session are handled
      one at a time, so they can't get around the document limit.
  - Document list: the session database now also records each document, which
    makes listing documents and checking the limit quick.
  - Endpoints:
    - POST /api/sessions/{id}/documents uploads files.
    - GET /api/sessions/{id}/documents lists them.

    Errors name the file that caused them, for example {"detail": "...",
    "filename": "bad.docx"}.
  - Oversized uploads: a request that is too large overall is rejected before
    it's read, and at most one byte over the file-size limit is read per file.
  - Cleanup: deleting a session, or a session expiring, now also removes its
    indexed documents.
  - Tests: there are 25 new tests. They use a fast fake embedder, and one slow
    test uses the real model. Run it with pytest -m slow.

  Measured on the live server: a 200-page PDF (1,000 chunks) is indexed in about
  2.8 seconds. That confirms synchronous ingestion is fine within the limits,
  and I've noted it in plan.md along with the all-or-nothing and duplicate
  rules.

  What was added:
  - Claude calls in app/llm.py stream the answer from the model set in LLM_MODEL
    (default claude-sonnet-5). Thinking stays on, and a new setting LLM_EFFORT
    (default medium) trades speed against thoroughness. I raised LLM_MAX_TOKENS
    to 16000 because thinking tokens count towards that cap.
  - Error handling: errors from the Anthropic SDK become short messages that are
    safe to show users, such as an invalid key, an unknown model, rate limiting
    or a network failure.
  - Grounding in app/rag.py:
    - Rules: the system prompt tells Claude to answer only from the retrieved
      passages and to cite them as [1], [2].
    - No answer: when the documents don't cover the question, Claude replies
      with a fixed "couldn't find" message.
    - Prompt injection: text inside the documents is treated as reference
      material, not instructions.
    - Passage format: passages are sent to Claude numbered, with the file name
      and page.
  - Endpoint: POST /api/sessions/{id}/query streams events to the browser:
    a. sources: the retrieved passages.
    b. delta: pieces of the answer as they arrive.
    c. done (with the source numbers actually cited and token usage) or error.

    It rejects empty or overlong questions, and returns 409 if the session has
    no documents yet.
  - Follow-up questions:
    - History: the browser sends recent turns, trimmed to the last 6 pairs.
    - Retrieval: the previous question is added to the search, so "what about
      the second one?" still finds the right passages.
  - Tests: there are 30 new tests covering prompt building, history trimming,
    the event stream, keeping sessions separate, the top-k limit, input checks
    and how each error type is reported.
